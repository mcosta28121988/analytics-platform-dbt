## Decisions

| # | Finding | Decision | Implemented in |
|---|---|---|---|
| D1 | 789 review_ids map to more than one order (1,603 rows) | Review key = `review_id + order_id`. Aggregate to order grain before joining to orders. | staging tests, `int_order_reviews_aggregated` |
| D2 | Fanout risk: 9,803 orders have more than 1 item (max 21), 2,961 more than 1 payment (max 29), 547 more than 1 review | Aggregate every child table to order grain in intermediate before joining. Add tests that row counts are unchanged at order grain. | intermediate + tests |
| D3 | 99,441 `customer_id` vs 96,096 `customer_unique_id` | `customer_id` is a per-order key. `dim_customers` grain = `customer_unique_id`. All repeat/LTV/cohort logic uses it. | `dim_customers`, `int_customer_orders` |
| D4 | 23,995 customer zip prefixes have a leading zero | Zip prefixes are `varchar` in every layer, never numeric | staging |
| D5 | 610 products with null category; 2 categories without translation (`pc_gamer`, `portateis_cozinha_e_preparadores_de_alimentos`) | Null → `unknown`. Add the 2 missing English names as our own additions (flagged) in a dbt seed. | seed + `dim_products` |
| D6 | 775 orders with no items; 1 with no payment | Keep in `fct_orders` with `has_items` / `has_payment` flags. Excluded from revenue KPIs. | `fct_orders` |
| D7 | 382 / 98,665 orders: payments ≠ items + freight (max R$182.81) | Revenue = `price + freight_value` from items (`gross_merchandise_value`). Payment value is a separate measure. Reconciliation test with a tolerance; root cause investigated in Phase 5. | `fct_orders`, custom test |
| D8 | 8 delivered orders without delivery date; 6 non-delivered with one; 1,359 handed to carrier before approval | Keep all rows. Add validity flags; exclude flagged rows only from the duration KPIs they break. | `int_orders_enriched` |
| D9 | 6,534 delivered orders arrived after the estimate | `is_late = delivered_customer_date::date > estimated_delivery_date`, for delivered orders with a valid delivery date only | `mart_delivery_performance` |
| D10 | Odd values: 9 payment lines ≤ 0, instalments = 0, product weight 0 g, a shipping_limit_date in 2020 | Range tests with `severity: warn`, documented, not corrected | staging YAML |
| D11 | Orders span 2016-09 to 2018-10, but only Jan 2017 – Aug 2018 is dense | Default KPI reporting window = 2017-01-01 to 2018-08-31. `dim_date` = 2016-01-01 to 2018-12-31. Daily replay runs over the dense window. | marts, `dim_date`, replay |
| D12 | Source typos `product_name_lenght`, `product_description_lenght` | Raw unchanged; renamed to `*_length` in staging | `stg_olist_products` |

## Known limitations (state these in the README / interviews)

- The dataset is a static sample (about 100k of Olist's orders), anonymised, and covers
  2016–2018. Any "daily" behaviour is simulated (see ADR 0001).
- Prices are in BRL. There is no currency or tax information.
- Customer and seller identities are anonymised hashes. Names and exact addresses aren't available.
